# 1 文档说明

## 1.1 编写目的

本文档依据《QX0002_报关单和放行单等单据处理流程_pdd_v1.2》编制，将业务需求与流程定义转化为可实现、可测试、可运维的程序设计方案，明确系统架构、模块划分、配置与数据结构、页面与接口适配方式、关键算法、异常处理、日志通知及部署要求。

本文档是开发、测试、实施与运维工作的共同依据：开发人员按本文档编码，测试人员按本文档设计用例，实施人员按本文档准备环境与配置，运维人员按本文档执行日常检查与故障处置。

当业务规则发生变化时，应先更新 PDD 与本文档，再变更代码，避免代码与需求脱节。

## 1.2 适用范围

适用于谦信化工报关单和放行通知单等单据处理流程（项目编号 QX0002）的 RPA 程序开发与交付。

覆盖 PDD 第 4.3 章中本期范围内的操作：读取配置、通过 RPUSI NetworkUSB 启用/关闭 U 盾、登录电子口岸/单一窗口、查询并导出报关单列表、筛选未上传附件报关单、下载报关单详情及六类单据、BIP 销售报关单录入与附件上传、报关信息绑定、更新运行结果表与结果反馈。

不覆盖 PDD 未描述的操作；不覆盖 OA 单证归集及 QX0003 电子档案管理（单证归集与打印）的内部实现，本流程不再触发归集、不上传 OA 附件。

本期按单机、单机器人、串行处理设计，不实现多机器并行与任务分片。

# 2 需求与流程概述

## 2.1 业务背景与目标

谦信化工出口业务需按公司（珠海、泰兴、横琴、荆门）分别使用对应 U 盾登录单一窗口与电子口岸，下载报关单、放行通知单、电子委托协议、发票、装箱单及保税核注清单，并在 BIP 中完成销售报关单录入、附件上传与报关信息绑定。

该工作重复度高、单据种类多、命名与存放规则严格，且需要跨 4 家公司的 U 盾切换。RPA 程序的目标是：在无人值守（或前台自动运行）条件下完成上述操作，保证单据完整、命名规范、BIP 数据准确、绑定结果可追溯，并按公司及出口年度输出运行结果与通知。

## 2.2 流程范围

| 范围 | 内容 |
| --- | --- |
| 范围内 | PDD 4.3 章节中本期范围内的操作：盾启用/关闭（RPUSI NetworkUSB）、登录与盾切换、报关单列表导出、未上传附件比对、六类单据下载与命名存储、BIP 销售报关单新增与附件上传、报关信息绑定、运行结果表更新与通知 |
| 范围外 | PDD 未提及的操作；OA 单证归集及 QX0003 内部实现；多机器并行；BIP/单一窗口/电子口岸的系统改造；人工业务判断（如无合同号、多合同号的处理决策） |
| 运行模式 | 1 台机器、1 个后台机器人、串行处理；可配置定时任务或手动触发 |
| 处理对象 | 出口、已结关、最近操作时间在配置窗口内、且 BIP 尚未上传附件的报关单 |

## 2.3 业务处理总览

| 序号 | 环节 | 系统 | 输入 | 输出 | 执行方 |
| --- | --- | --- | --- | --- | --- |
| 1 | 盾启用/关闭与登录 | RPUSI NetworkUSB、电子口岸/单一窗口 | 公司、U 盾端口 | 登录态会话 | 机器人 |
| 2 | 导出报关单列表 | 单一窗口 | 企业类别、进出口标志、是否结关、最近操作时间 | 报关单列表 Excel | 机器人 |
| 3 | 筛选未上传附件报关单 | 本地处理 + BIP 数据 | 报关单列表、BIP 已上传附件数据 | 待处理报关单号清单 | 机器人 |
| 4 | 下载单据 | 单一窗口/电子口岸 | 报关单号 | 报关单、放行通知单、电子委托协议、发票、装箱单、保税核注清单 | 机器人 |
| 5 | BIP 录入 | BIP | 报关单详情 Excel、映射表、汇率 | 销售报关单（草稿/已保存） | 机器人 |
| 6 | 附件上传与绑定 | BIP | 下载的单据、合同号 | 已上传附件、已绑定明细 | 机器人 |
| 7 | 结果与通知 | 本地/企微/邮件 | 逐单处理结果 | 运行结果表、通知消息 | 机器人 |
| 8 | 补跑 | 各系统 | 上期失败清单、BIP 单据状态 | 更新后的结果表 | 机器人 |

## 2.4 触发方式与入参

流程由定时任务或人工手动触发，运行时提供以下入参：

| 入参 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 公司列表 | 字符串数组 | 是 | 珠海、泰兴、横琴、荆门，可多选（用中英文逗号隔开）；决定使用的 U 盾及输出目录 |
| 最近操作时间期间 | 日期区间或天数 | 否 | 默认取配置中的 62 天；单一窗口单次查询最多 7 天，程序自动分段 |
| 运行模式 | 枚举 | 否 | 正常 / 补跑；补跑时额外读取上期失败清单 |
| 调试开关 | 布尔 | 否 | 保留浏览器窗口、输出更详细日志，仅测试环境使用 |

入参由调度平台通过命令行参数或配置文件传递。建议采用命令行方式，例如：

```text
python main.py --companies 珠海,泰兴 --recent-days 62 --mode normal
python main.py --companies 珠海 --mode rerun
```

## 2.5 关键约束

必须通过 RPUSI NetworkUSB 开启对应公司的 U 盾端口才能登录电子口岸/单一窗口；切换公司时先关闭原端口、开启新端口，并重新登录，不能复用会话。

机器人运行期间，共享盘中的结果表、日志、输出单据不得被用户打开，否则读写会失败；用户查看时应复制到本地。

部署在用户电脑时，运行期间不能关机、锁屏，浏览器与分辨率需统一。

所有单据最终以导出的 Excel 版报关单为准，页面展示值仅用于校验。

报关单与 BIP 的数据映射不写死在代码中，必须通过配置表维护。

# 3 总体设计

## 3.1 设计原则

| 原则 | 落地方式 |
| --- | --- |
| 配置驱动 | 系统地址、账号、公司盾端口、查询天数、分段天数、重试次数、字段映射、通知渠道均放入 01_Config/config.xlsx，代码不写死业务参数 |
| 单号级幂等 | 以报关单号为最小处理单元，处理前检查 BIP 已上传附件与运行结果表，避免重复上传附件与重复录入 |
| 失败隔离 | 单个报关单下载或录入失败不终止整批；仅登录失败、U 盾异常、配置错误等全局问题终止流程 |
| 可追溯 | 每单记录状态、异常类型、异常原因、重试次数、耗时、生成文件清单、BIP 绑定明细与结果表状态 |
| 人工兜底 | 无合同号、多合同号、绑定不唯一等业务异常不做猜测处理，标记人工处理，修正主数据后再进入补跑 |
| 与框架解耦 | 业务流程放在 workflows，系统操作放在 web，公共能力复用 config/core/utils/data_processing |

## 3.6 与现有框架的集成方式

main.py 负责加载 config.xlsx、初始化日志与环境，然后实例化 Qx0002MainTask 并调用 run()。

Qx0002MainTask 继承 TaskBase，在 execute() 中按公司循环组装子任务；子任务之间通过 TaskContext 传递当前公司、待处理清单、逐单结果等。

各系统适配类继承 BasePage 或独立封装，浏览器实例由 BrowserManager 创建，并按系统名存入 TaskContext.browsers。

配置读取沿用 ConfigLoader 的 sheet.key 方式；公司盾配置、字段映射为二维表，需要扩展 read_table(sheet) 方法返回字典列表。

日志沿用 log/loggingConfig.py，业务日志同时写入 04_Log，便于运维按公司、按单号检索。

# 6 数据设计

## 6.1 数据流

报关单列表（单一窗口导出）经过比对生成待处理清单；逐单下载形成本地文件集合；报关单详情 Excel 经解析后形成 BIP 录入数据与文件名要素；BIP 绑定结果回写到运行结果表；运行结果表再作为补跑去重与通知的数据源。

```text

                    ├── 比对/去重 ──► 待处理清单（报关单号）
BIP已上传附件数据 ──┘                        │

                    逐单下载 ──► 本地单据文件 + 报关单详情Excel
                                             │
                                             ▼
                    BIP录入/上传/绑定 ──► 绑定结果（明细行、单据号）
                                             │
                                             ▼
                                  运行结果表 ──► 通知/补跑
```

# 8 流程详细设计

## 8.1 主流程

主流程按公司串行执行。每家公司完成盾端口切换、登录、查询、下载、BIP 录入、绑定与结果更新后，再切换到下一家公司。公司内部按报关单号串行处理，单个单号失败不影响后续单号。

```python
class Qx0002MainTask(TaskBase):
    def execute(self) -> bool:
        companies = load_companies(self.params)
        all_summaries = []
        for company in companies:
            ctx = CompanyContext(company)
            try:
                if not InitSubtask(ctx).run():      # 配置、目录、RPUSI 端口
                    raise GlobalException('初始化失败')
                list_files = DeclarationSubtask(ctx).run()   # 登录+导出+比对
                if not list_files:
                    all_summaries.append(empty_summary(ctx))
                    continue
                DownloadSubtask(ctx).run()          # 逐单下载，失败隔离
                BipEntrySubtask(ctx).run()          # 逐单录入+上传附件
                BindingSubtask(ctx).run()           # 逐单绑定，记录待补跑
            except LoginException as e:
                mark_company_failed(ctx, e)         # 登录失败终止本公司
            except Exception as e:
                mark_company_failed(ctx, e)         # 未预期异常，保留现场
            finally:
                ResultSubtask(ctx).run()            # 写结果表
                all_summaries.append(ctx.summary)
                close_sessions(ctx)
        NotifySubtask(all_summaries).run()          # 企微+邮件
        return True
```

> 说明：上方为结构示意，实际实现中每个子任务的 execute() 返回布尔值表示“是否可继续”。下载与录入阶段不因单号失败返回 False，只有全局登录/配置失败才中断本公司。

## 8.3 登录与盾端口切换

U 盾是登录电子口岸/单一窗口的前提。本流程使用 RPUSI NetworkUSB 集中管理 4 个 U 盾的端口开关，机器人不直接插拔 U 盾。

- 每家公司对应一个固定端口，端口映射在 5.3 公司盾配置中维护。
- 登录前：调用 RPUSI 控制接口关闭其他公司端口（或确认其他端口已关闭），开启当前公司端口，等待设备就绪。
- 登录后：以页面显示的企业名称二次校验，确认端口与公司匹配，避免串号。
- 切换公司：先退出登录并关闭浏览器上下文，再关闭当前端口、开启下一公司端口，然后重新登录。
- 端口离线、开启失败、被占用或设备不可达：按系统异常重试；仍失败终止本公司并通知运维。
- RPUSI 的具体控制方式（HTTP API、CLI 或管理页面）以设备说明书为准，统一封装在 utils/usbhub.py，业务层不直接操作设备。

```python
from utils.usbhub import UsbHub

hub = UsbHub(config.get('系统配置.RPUSI控制地址'))

def switch_company(company):
    hub.power_off_all()                      # 关闭全部端口，避免多公司证书同时可用
    hub.power_on(company.usb_port)           # 开启当前公司端口
    hub.wait_ready(company.usb_port, timeout=30)
    if not hub.is_on(company.usb_port):
        raise UsbHubError(f'RPUSI 端口开启失败: {company.name}-{company.usb_port}')
```

> 说明：端口开关后系统识别证书可能需要数秒，登录前需等待“端口就绪”，不能仅凭开关指令返回成功就进入登录页。

## 8.4 查询并导出报关单列表

单一窗口的“最近操作时间”（入参，不传默认62）单次最多查询 7 天。程序按“今天向前、每段 7 天”拆分查询窗口，逐段查询列表导出后合并成一个XXX公司-报告单列表-YYYYMMDD HHMMSS.xlsx，导出的非最后的文件可以存储在临时文件，覆盖配置的 62 天范围。

```python
from datetime import timedelta

def build_windows(today, total_days=62, step=7):
    windows, end, remain = [], today, total_days
    while remain > 0:
        span = min(step, remain)
        start = end - timedelta(days=span - 1)
        windows.append((start, end))
        end = start - timedelta(days=1)
        remain -= span
    return windows
```

62 天共拆为 9 段：8 段各 7 天，最后 1 段 6 天；段与段之间不重叠。

每段查询的固定条件：

- 企业类别：报关收发货人

# 9 关键算法与业务规则

## 9.1 时间窗口与跨年规则

报关单的归属年度由其“出口日期”决定，而不是运行日期。查询窗口使用“最近操作时间”（默认 62 天，按 7 天分段），下载单据按出口日期所属年月归档，运行结果表与邮件附件按出口年度划分。因此在 1 月初或查询窗口跨越年末时，同一次任务需要同时处理两个年度。

| 场景 | 处理规则 |
| --- | --- |
| 查询窗口跨年 | 按出口日期分别写入对应 YYYYMM 目录与年度结果表 |
| 单次查询上限 | 按 7 天分段，段间不重叠；合并后按报关单号去重 |
| 补跑跨年 | 同时读取今年与去年的运行结果表和 BIP 已上传附件数据 |
| 邮件附件 | 跨年时附两个年度的结果表，正文注明各自数量 |
| 文件名 | 出口日期使用报关单实际日期，不使用运行日期 |
| 汇率 | 按出口日期所属月份 1 号取值，跨年不特殊处理 |

## 9.3 明细汇总与精度

BIP 表头的报关数量、总价取报关单明细汇总值，报关单价 = 汇总总价 / 汇总数量。计算必须使用 Decimal，禁止直接用二进制浮点数累加，避免出现 0.01 级误差导致绑定失败。

```python
from decimal import Decimal, ROUND_HALF_UP

def summarize(lines):
    qty = sum((Decimal(str(l.qty)) for l in lines), Decimal('0'))
    amount = sum((Decimal(str(l.amount)) for l in lines), Decimal('0'))
    if qty == 0:
        raise BusinessError('汇总数量为 0')
    price = (amount / qty).quantize(Decimal('0.01'), rounding=ROUND_HALF_UP)
    return qty, amount, price

# 币种精度：默认 2 位；JPY 等无小数币种按配置取 0 位
# 汇总结果同时保留原始值，用于结果表追溯
```

若报关单明细存在多行且币种、单价不一致，仍需按行汇总，不得只取第一行。汇总结果与明细不一致时，以明细为准并记录校验日志。

## 9.4 报关信息绑定匹配

绑定匹配以报关单的汇总数量 Q、汇总金额 A 为目标，在 BIP 指定合同号查询出的明细行中寻找候选。匹配必须满足“数值一致且唯一”，任何不唯一的情况都转人工，禁止程序自行选择。

### 9.4.1 匹配规则

| 优先级 | 规则 | 结果 |
| --- | --- | --- |
| 规则一 | 单行数量与金额均与报关单汇总值一致（容差内） | 仅一行命中则绑定该行；多行命中则进入规则二判定 |
| 规则二 | 多行组合的数量汇总、金额汇总均与报关单一致，且组合唯一 | 绑定该组合全部行 |
| 规则三 | 无命中、组合不唯一、或命中多个组合 | 不绑定，标记需人工或待补跑 |

### 9.4.2 判定流程

```python
def match_binding(decl, lines):
    Q, A = decl.total_qty, decl.total_amount
    # 规则一：单行精确匹配
    single = [l for l in lines if eq(l.qty, Q) and eq(l.amount, A)]
    if len(single) == 1:
        return BindingResult(mode='single', lines=single)

    # 规则二：多行组合匹配（含数量与金额双条件）
    solutions = find_subsets(lines, Q, A, max_results=2, max_lines=20)
    if len(solutions) == 1:
        return BindingResult(mode='group', lines=solutions[0])
    if len(solutions) > 1:
        return BindingResult(mode='ambiguous', reason='存在多个匹配组合')
    return BindingResult(mode='none', reason='未找到匹配明细')
```

### 9.4.3 组合算法

组合匹配本质是带双约束的子集和问题。为保证单机运行的可控性，采用带剪枝的深度优先搜索：按金额降序排序，金额前缀和剪枝；金额换算为最小货币单位（分）后用整数计算；数量使用 Decimal 比较。找到第 2 个解即停止，用于判断“唯一”。

```python
def find_subsets(lines, target_qty, target_amount, max_results=2, max_lines=20):
    items = sorted(lines, key=lambda x: x.amount, reverse=True)
    if len(items) > max_lines:
        return []                      # 超出规模转人工，避免指数爆炸
    suffix_amount = suffix_sums(items, 'amount')
    suffix_qty = suffix_sums(items, 'qty')
    results = []

    def dfs(i, chosen, qty, amount):
        if len(results) >= max_results:
            return
        if eq(qty, target_qty) and eq(amount, target_amount) and chosen:
            results.append(list(chosen))
            return
        if i >= len(items):
            return
        if amount > target_amount + TOL or qty > target_qty + TOL_Q:
            return
        if amount + suffix_amount[i] < target_amount - TOL:
            return
        # 不选第 i 行
        dfs(i + 1, chosen, qty, amount)
        # 选第 i 行
        chosen.append(items[i])
        dfs(i + 1, chosen, qty + items[i].qty, amount + items[i].amount)
        chosen.pop()

    dfs(0, [], Decimal('0'), Decimal('0'))
    return results
```

复杂度最坏为 O(2^n)，通过 max_lines=20、金额前缀剪枝、金额/数量上界剪枝与“找到 2 个解即停止”控制耗时。若同一合同下明细行超过 20 行，直接转人工，并在结果表记录原因。

### 9.4.4 合同号特殊处理

报关单无合同号：无法查询绑定，运行状态记“需人工”，绑定状态记“失败，无合同号”。

报关单有多个合同号：运行状态记“需人工”，绑定状态记“失败，多个合同号”，不尝试自动绑定。

荆门合同号表头与表体可能不同：按 BIP 顾问提供的 SQL 同时记录表头、表体合同号，通过报关单号关联后再匹配；匹配规则与普通场景一致。

同一合同号下存在多个报关单待绑定：绑定前先排除已被其他报关单占用的明细行，避免重复绑定。

```python
def ensure_writable(path, retries=5, interval=3):
    for i in range(retries):
        try:
            with open(path, 'a'):
                pass
            return True
        except PermissionError:
            time.sleep(interval)
    return False
```

## 10.2 重试策略

统一使用 utils/helpers.py 的 retry 装饰器，禁止在各处手写循环重试。

系统类异常（网络、超时、页面未就绪）重试；业务类异常（数据不合法、无合同号）不重试。

重试间隔按固定或指数退避，并在日志中记录第几次重试与失败原因。

重试前恢复现场：刷新页面、重新进入节点、重新登录（会话失效时）。

达到上限后按 10.1 的“处理结果”落状态，不在同一单上无限重试。

```python
from utils.helpers import retry

@retry(max_attempts=2, delay=2.0)
def download_release_note(self, decl, target):
    self.query_by_no(decl.no)
    with self.page.expect_download(timeout=self.download_timeout) as dl:
        self.page.get_by_role('button', name='打印预览').click()
    dl.value.save_as(str(target))
    if not target.exists() or target.stat().st_size == 0:
        raise DownloadError(f'放行通知单下载失败: {decl.no}')
```

## 10.4 失败隔离与继续策略

失败隔离的边界是“报关单号”。下载、录入、绑定任一阶段失败，都只影响当前单号，后续单号继续处理。只有配置错误、登录失败、U 盾异常、浏览器崩溃等全局问题才终止当前公司或整个流程。

| 失败阶段 | 后续动作 |
| --- | --- |
| 报关单详情下载失败 | 无法解析，跳过该单的 BIP 录入；其余单据若已下载保留 |
| 部分单据下载失败 | 继续 BIP 录入，附件只上传成功部分；结果表对应路径列留空，异常原因注明缺失单据 |

| 绑定失败 | BIP 单据保留；结果表记录待补跑/需人工 |
| 结果表写入失败 | 保留内存结果，写临时文件重试；仍失败发送告警并输出 CSV 备份 |

# 12 安全性设计

## 12.1 凭据管理

系统密码优先存入 Windows 凭据管理器，由操作系统加密；配置表只保存“凭据目标名”，不保存明文密码。程序通过 keyring 或 win32cred 读取，读取失败时不回退到明文，直接终止并提示管理员维护凭据。

| 方案 | 适用场景 | 实现方式 | 说明 |
| --- | --- | --- | --- |
| Windows 凭据管理器（推荐） | 正式主机、业务操作员较少 | keyring.set_password/get_password 或 win32cred | 密码由操作系统加密，支持集中维护 |
| 配置表（备选） | 测试环境或临时使用 | config.xlsx 中保存加密串 | 上线前必须切换为凭据管理器 |
| 环境变量 | 调试/自动化部署 | 启动脚本注入 | 不得写入代码仓库 |

```python
import keyring

def get_password(target_name: str) -> str:
    pwd = keyring.get_password('QX0002', target_name)
    if not pwd:
        raise ConfigError(f'凭据不存在，请在 Windows 凭据管理器中维护: {target_name}')
    return pwd
```

## 12.2 权限与文件安全

共享盘目录由 IT 设置权限，仅 RPA 账号与业务相关人员可读写。

程序运行账号应具备最小权限，不授予管理员权限。

输出单据与结果表不允许普通用户删除，避免误操作导致补跑数据缺失。

Scripts、日志与截图中不得出现身份证号、银行账号等敏感信息；确需记录时脱敏。

临时文件在运行结束后清理，避免残留单据副本。

## 12.3 操作审计

每单记录处理时间、操作账号（RPA 专用账号）、BIP 单据号与绑定明细。

关键操作（提交、绑定、上传）前后各记录一条日志，便于回溯。

> 说明：人工在 BIP 完成处理后，不需要手工改结果表；下次补跑会根据 BIP 已上传附件数据与单据状态，将“失败”更新为“成功-人工已处理”。
